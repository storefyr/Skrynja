# M0.0 — Målerapport: Findes `vibe-acp` på målmaskinen?

**Dato:** 2026-10-26
**Målmaskine:** Jolla Phone (2026), Sailfish OS 5.x, aarch64
**Målemetode:** Web-research (ingen kodeændringer, ingen API-kald)
**Lag:** L3 (agenten selv)

---

## Spørgsmål (fra vejkortet §8)

> Findes `vibe-acp` på målmaskinen, i hvilken version, under hvilken licens?

## Resultat: NEJ — med forbehold

`vibe-acp` findes **ikke** som en pakke til Sailfish OS, hverken i Jollas officielle
repositorier, OpenRepos eller SailfishOS:Chum. Der er ingen `python3-mistral-vibe`
eller tilsvarende. For at køre `vibe-acp` på en Sailfish-enhed skal den installeres
manuelt, hvilket bringer os til næste spørgsmål.

---

## Underliggende krav (blokerende)

### 1. Python-version — KRITISK KONFLIKT

| Kilde | Krav |
|---|---|
| `mistral-vibe` pyproject.toml (v3.0.2) | `requires-python = ">=3.12"` |
| Sailfish OS (Rokua 3.3, 2020) | Python 3.8.1 |
| Sailfish OS forum (nov 2025) | Python 3.11 update **merged** (ikke nødvendigvis udrullet) |
| **Mål:** Jolla Phone 2026, Sailfish 5.x | **Ubekræftet — sandsynligvis 3.8 eller 3.11** |

`vibe-acp` kræver **Python ≥ 3.12**. Sailfish OS har (senest bekræftet) Python 3.8,
med en Python 3.11-opdatering undervejs (merged november 2025). Selv med 3.11 er
kravet ikke opfyldt. **Der skal Python ≥ 3.12 til for at køre vibe-acp overhovedet.**

### 2. Afhængigheder — OMFATTENDE

`mistral-vibe` har **~90 direkte afhængigheder** (fra pyproject.toml v3.0.2), inkl.:

- `agent-client-protocol==0.11.0` (ACP Python SDK)
- `pydantic==2.13.4`, `pydantic-core==2.46.4` (har C-extension — kræver kompilering)
- `cryptography==50.0.0` (har C/Rust-extension — kræver kompilering)
- `tree-sitter==0.26.0`, `tree-sitter-bash` (C-extension)
- `rpds-py==0.30.0`, `zstandard==0.25.0` (Rust/C-extensioner)
- `textual==8.2.8`, `rich==15.0.0` (terminal UI — irrelevant for ACP, men påkrævet)
- `httpx`, `mcp==1.28.1`, `mistralai==2.6.0`, `gitpython`, `websockets`, m.fl.

**Mange af disse har native C/Rust-extensioner** (`.so`-filer), som skal kompileres
specifikt for aarch64 Sailfish OS. Der findes ingen præbyggede hjul (wheels) til
Sailfish OS. Dette er ikke `pip install mistral-vibe` på en telefon — det er en
fuld cross-kompileringsopgave.

### 3. Byggesystem — KOMPLEKST

`mistral-vibe` bruger **maturin** som bygge-backend og inkluderer en **Rust
extension** (`mistralai_vibe_local_harness._native`). Det betyder:

- Kræver Rust toolchain på aarch64
- Kræver maturin
- Kræver en C/C++ kompiler til native Python-extensioner

Ingen af disse er standard på Sailfish OS.

### 4. Licens

`mistral-vibe` er **Apache-2.0** — kompatibel med GPL-3.0-only (Apache-2.0 er
permissiv, GPL-3.0 er copyleft; Apache-2.0-kode kan godt indgå i et GPL-3.0-projekt).
Licensen er **ikke** problemet.

## Harbour-regler (Jolla Store) — BLOKERENDE for lokal kørsel

Fra [harbour.jolla.com/faq](https://harbour.jolla.com/faq):

| Regel | Relevans |
|---|---|
| **"Python is allowed in connection with PyOtherSide"** | Python-apps skal bruge PyOtherSide (QML↔Python bridge). En ACP-agent som underproces er ikke PyOtherSide. |
| **"the RPM file containing the application must include all the needed Python-libraries"** | Alle ~90 afhængigheder + Python ≥ 3.12 selv skal pakkes i RPM'en. |
| **"No, and we currently do not plan to support that"** (om Perl/Ruby/andre sprog) | Jolla har ikke planer om at understøtte vilkårlige sprogruntimes ud over Python+PyOtherSide. |
| **Ingen `%post`-scripts** | Kan ikke køre `pip install` ved installation. |
| **Ingen SUID/SGID** | Ingen privilege escalation. |
| **Filer kun i `/usr/share/<app>/`** | En Python-agent + interpreter + ~90 pakker fylder nemt 100-300 MB. Harbour FAQ'en advarer eksplicit mod store præinstallerede datafiler. |
| **Bundled tredjeparts-binærer** | Forumdiskussion (Ferry Sync/rclone, postivene) viser at bundling af eksterne eksekverbare i `/usr/bin/` møder modstand fra QA — selvom `/usr/share/<app>/libexec/` nu er tilladt (PR #189 til rpmvalidator). |

**Konklusion:** At bundle `vibe-acp` + Python 3.12 + ~90 afhængigheder (mange med
native extensioner) i en Harbour-RPM er **ikke realistisk**. Det ville:
1. Kræve cross-kompilering af Python 3.12 + Rust toolchain + alle native deps til aarch64 Sailfish
2. F fylde 100-300+ MB (mod Harbour's eksplicitte anbefaling mod store pakker)
3. Møde QA-modstand (bundled interpreter = "workaround of security limitations")
4. Bryde Sailjail-sandboxing (agenten skal have adgang til filsystem, shell, netværk)

---

## Sailjail-sandboxing — YDERLIGERE BLOKERENDE

Sailfish OS 4.4+ kører alle Harbour-apps i en **Sailjail-sandbox**. En ACP-agent
som `vibe-acp` er designet til at:
- Læse og skrive filer i projektmapper
- Køre shell-kommandoer
- Tilgå git
- Oprette netværksforbindelser

Sailjail begrænser netop dette. En kodningsagent i en Sailjail-sandbox er
fundamentalt i konflikt med sandboxens formål.

|---|---|---|
| A | Bundle vibe-acp i Skrynja-RPM'en | **Afvist** — for komplekst, for stort, Harbour QA vil afvise |

| Spørgsmål | Svar |

| Under hvilken licens? | Apache-2.0 (ikke problemet) |
| Kan det pakkes til Harbour? | **Nej** — størrelse, sandboxing, QA-politik |
| **Kan vejkortet fortsætte som planlagt?** | **Nej — ikke med lokal agent på telefonen** |

### Næste skridt (anbefaling)

M0.0 afslører et **arkitektonisk vejskel**. Vejkortets Trin A (A2 transportvalg,
A7 sprog/kørselsvalg) skal genovervejes:

1. **Hvis målet er lokal agent på telefonen:** Vejkortet skal omskrives. Enten
   bygges en minimal ACP-agent direkte i Skrynjas C++-kode (alternativ E), eller
   vejkortet opgives.

2. **Hvis målet er ACP-klient til ekstern agent:** Skrynja bliver en klient der
   forbinder til en `vibe-acp` (eller anden ACP-agent) over netværk. Dette er
   teknisk muligt, men ændrer produktet fra "chat med Mistral" til "fjernstyring
   af en kodningsagent" — og kræver at brugeren har en server med vibe-acp.

3. **Hvis målet er at beholde nuværende produkt:** Skrynja fortsætter som
   Mistral Conversations API-klient. Vejkortet arkiveres.
